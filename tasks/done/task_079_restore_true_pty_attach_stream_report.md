# Task Report

## Task ID
`task_079_restore_true_pty_attach_stream`

## Summary
- Replaced the 200 ms `session.viewport` polling attach client with a true lossless PTY-stream attach: the controller now broadcasts every raw PTY output chunk to attached clients via a new typed `stream` IPC notification (`IpcStreamFrame`), and `airelay attach <session>` writes those raw chunks verbatim to the local terminal — no clear/redraw, no line reduction, no injected `\x1b[2J\x1b[H`. Raw input and resize still ride the existing immediate narrow IPC path and never append Enter.
- Added a bounded attach bootstrap: the controller keeps a raw output ring (max `256 KiB` / 8192 chunks) and, on `session.attach`, synchronously registers the socket, replays the ring, and writes the success response back-to-back so the client receives `[replay, success, live]` with no output race or duplicated bytes at the attach boundary. Stream frames are JSON-encoded with embedded newlines escaped, so they cannot break the newline-delimited IPC framing.
- Fixed the observed live regression: a detached runtime whose own controller socket vanished while the runtime PID stayed alive previously remained a live-looking `detached.json` entry with an unusable session (later pruned, making `airelay prompt` report "Session not found"). A new supervised watchdog now probes the runtime's own controller endpoint every `AIRELAY_DETACHED_WATCHDOG_MS` (default 2000 ms) and, after `CONTROLLER_FAULT_LIMIT` (`2`) consecutive failures, self-terminates the agent via the PTY so the normal `finally` cleanup removes the registry and session records — a runtime with no reachable controller can no longer look live.
- Made shutdown bounded: `controller.stop()` now force-destroys attached sockets and adds a 2000 ms `STOP_TIMEOUT_MS` fallback via `closeAllConnections`, so a stuck raw-input client can never keep the runtime process alive with a dead controller. Slow clients are detached deterministically above a per-socket `STREAM_MAX_BUFFERED_BYTES` (256 KiB) write cap; buffered pre-reader stream frames are capped at `BOOTSTRAP_BACKLOG_CAP` (8192).
- Preserved ordinary `airelay start` direct-PTY behavior (regression-tested) and the `prompt`/`interrupt` controller paths; the compat path produces a clear structured error ("Unknown method ... Session controller may be older than this CLI.") when the controller lacks `session.attach`.
- Made the attach detach boundary explicit and tested after a later live test showed Ctrl-C ambiguity: only Ctrl-D (0x04)/EOF/terminal-close detach the client without stopping the runtime; Ctrl-C (0x03) is documented and tested as raw harness input forwarded verbatim to the runtime PTY (never an attach escape). If the harness exits on it, the runtime's exit cleanup removes the registry/session — mirroring the reported opencode Ctrl-C-exit behavior.

## Source Audit Findings
- Old attach was a pure polling client: `createAttachTransport.requestViewport()` → `session.viewport` → controller's headless xterm snapshot lines; `AttachClient` ran a 200 ms `setInterval`, and `renderViewport` did `\x1b[2J\x1b[H` + line-by-line print every tick. This discards raw output between polls, loses ANSI/control bytes, cursor/alternate-screen state, colors, wrapping, and blank rows, and cannot reproduce the original PTY — the headless terminal is a rendering approximation, not a record.
- Raw PTY output already flowed through one narrow channel (`run.ts` `onOutput` → `controller.feedOutput(chunk)` → headless xterm) before `session.viewport` re-derived it; input/resize already had immediate dedicated IPC (`session.input.raw` / `session.resize`, fire-and-forget with no reply). The smallest canonical extension is to fan out the same raw `feedOutput` chunk to attached sockets as a typed `stream` notification and have the client render it verbatim — no second store, no second PTY, no polling.
- `~/git/reporelay` (Rust) was inspected as a reference for PTY-stream attach patterns: it uses `portable_pty` with a master-reader thread, raw-mode guards, and resize-tick handling, and routes IPC over a unix socket. No direct JS attach-port source was present (remote/proprietary, not vendored) so it was treated as reference only; the framing/ordering design here was derived from this repo's own IPC conventions.
- IPC framing is `\n`-delimited JSON lines (`readLines`/`parseRequest`/`serializeResponse`). A raw chunk may contain `\n`,`\r`,ESC and multi-byte UTF-8, so the stream frame must escape embedded newlines — hence `serializeStreamFrame` JSON-encodes the whole chunk as a single string.
- Lifecycle gap: `controller.stop()` used a bare `server.close(finish)` that waits indefinitely for open connections; a lingering raw-input client (or any attached socket) could keep it unresolved, so the detached runtime process stayed alive with a dead controller socket — the exact observed "controller gone, runtime PID alive" state. This required the bounded shutdown + the runtime-side watchdog.

## IPC Ordering / Bootstrap  Guarantee
- On `session.attach` the controller runs the whole bootstrap synchronously with no `await`: register socket in `attachedClients` → replay the bounded raw ring (in order) → write the `success` response. Because `socket.write` preserves call order on a single socket, live `feedOutput` chunks arriving afterwards are appended after the replay and cannot interleave; the client therefore observes exactly `[replay, success, live]`. The replay is bounded (`256 KiB` / 8192 chunks) so it is memory-safe, and there is no second persistent transcript.
- The client registers its stream reader (`transport.onStream`) synchronously before sending `session.attach`, and the transport keeps a small ordered backlog (cap `8192`) for frames that arrive between connect and reader registration; backlog is replayed in order on registration, so no frame is dropped at the boundary.
- Limitation (documented): bytes produced before the bounded ring window (older than the ring cap) cannot be reconstructed exactly and are not shown; with active use the ~256 KiB window is several terminal screens of output, and everything after attach is lossless and live. This is the best bounded bootstrap supported without a second per-attach transcript, per the task.
- Default idle viewport snapshots (`session.viewport`) remain available as an explicit status API and are no longer used by the attach renderer.
